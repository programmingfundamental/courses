# Лабораторно упражнение 7

## Unit тестове

### Цел

Да се разработят unit тестове за част от бизнес логиката на приложението и да се анализира качеството на тестове, предложени от ИИ асистент.

Да се разграничат:
-	реален обект и mock;
-	happy path, negative path и boundary/edge case;
-	unit тестове и Spring integration тест;
-	тест на наблюдавано поведение и тест, зависещ от implementation details.

### Начално състояние

Да се използва референтното начално състояние на проекта след ЛУ 6.

Функционалността на приложението е реализирана, а част от бизнес логиката е обособена в специализирани services, включително WorkingTimeService, LoyaltyService и CancellationService.

### Кратка теория

*Unit test*

Unit тестът проверява малка, изолирана част от поведението на приложението – метод, клас, или отделна бизнес отговорност.

Unit тестът трябва да бъде:
-	бърз;
-	независим;
-	повторяем;
-	фокусиран върху конкретно поведение.

При unit тест не се стартира цялото Spring приложение, освен ако това не е необходимо за конкретния тип тест.

*Given – When – Then*

Всеки тест да бъде структуриран в три части:

```java
@Test
public void shouldReturnFalseAtStartOfWorkingHours() {
    // given
    LocalDateTime time = LocalDateTime.of(2026, 8, 10, 9, 0);

    // when
    boolean result = workingTimeService.isOutsideWorkingHours(time);

    // then
    assertFalse(result);
}
```

*JUnit 5*

JUnit е фреймуърк за автоматизирано тестване на Java приложения. В упражнението се използва JUnit 5 за създаване и изпълнение на unit тестове.

Тестовите класове обикновено се разполагат в директорията src/test/java, като пакетната им структура следва структурата на тествания код. Например за src/main/java/.../service/WorkingTimeService.java тестът може да бъде разположен в src/test/java/.../service/WorkingTimeServiceTest.java

Имената на тестовите класове обикновено завършват на Test.

*Анотация @Test*

Метод, който представлява отделен тестов случай, се означава с @Test.

```java
@Test
public void shouldRecognizeWorkingDay() {
    // given
    LocalDateTime dateTime = LocalDateTime.of(2026, 8, 10, 10, 0);

    // when
    boolean result = workingTimeService.isWorkingDay(dateTime);

    // then
    assertTrue(result);
}
```

Всеки тест трябва да проверява конкретно поведение и да има ясно очакван резултат. В упражненията тестовете се организират по структурата Given – When – Then:
-	given – подготвят се началните данни и необходимите обекти;
-	when – изпълнява се поведението, което се тества;
-	then – проверява се полученият резултат.

*Assertions*

Assertions се използват за сравняване на действителния резултат с очаквания. Често използвани са:
- assertEquals(expected, actual);
- assertTrue(condition);
- assertFalse(condition);
- assertNull(value);
- assertNotNull(value).

Например:

```java
@Test
public void shouldReturnNextWorkingDay() {
    // given
    LocalDateTime friday = LocalDateTime.of(2026, 8, 14, 10, 0);

    // when
    LocalDateTime result = workingTimeService.nextWorkingDay(friday);

    // then
    assertEquals(LocalDateTime.of(2026, 8, 17, 10, 0), result);
}
```

При тестовете не е достатъчно да се провери единствено, че резултатът не е null. Assertion-ът трябва да доказва конкретното очаквано поведение.

*Проверка за възникване на изключение*

Когато очакваното поведение е възникване на изключение се използва assertThrows():

```java
@Test
public void shouldRejectInvalidValue() {
    // given
    int invalidValue = -1;

    // when
    IllegalArgumentException exception = assertThrows(
            IllegalArgumentException.class,
            () -> service.execute(invalidValue)
    );

    // then
    assertNotNull(exception);
}
```

По-смислена проверка може да включва и вида или съдържанието на грешката, когато те са част от договора на метода.

*@BeforeEach*

Когато преди всеки тест е необходима еднаква начална подготовка, може да се използва @BeforeEach:

```java
private WorkingTimeService workingTimeService;

@BeforeEach
void setUp() {
    workingTimeService = new WorkingTimeService();
}
```

Метод с тази анотация се изпълнява преди всеки тестов метод. Това позволява тестовете да работят с независимо начално състояние.

Не е задължително да се използва подобна организация в случай на малък stateless service.

*Параметризирани тестове*

Когато едно и също поведение трябва да бъде проверено с различни входни стойности, вместо множество почти еднакви тестове може да се използва parameterized test, при който се използва анотацията @ParameterizedTest. Тестовите данни могат да бъдат зададени по различни начини.

Единият възможен начин е с използване на @ValueSource:

```java
@ParameterizedTest
@ValueSource(ints = {1, 2, 3, 4, 5})
public void shouldRecognizeWorkingDays(int dayOfWeek) {
    // given
    // ...

    // when
    // ...

    // then
    // ...
}
```

При повече от един параметър може да се използва @CsvSource:

```java
@ParameterizedTest
@CsvSource({
        "8, 59, true",
        "9, 0, false",
        "17, 59, false",
        "18, 0, true"
})
public void shouldDetermineOutsideWorkingHours(int hour, int minute, boolean expected) {

    // given
    LocalDateTime dateTime = LocalDateTime.of(2026, 8, 10, hour, minute);

    // when
    boolean result = workingTimeService.isOutsideWorkingHours(dateTime);

    // then
    assertEquals(expected, result);
}
```

Параметризираният тест е подходящ, когато се проверява едно и също правило за различни стойности. Не трябва да се обединяват несвързани сценарии само с цел намаляване броя на тестовите методи.

*Имена на тестовете*

Името на тестовия метод трябва да показва какво поведение се проверява; например:
- shouldRecognizeWeekendAsNonWorkingDay()
- shouldSkipWeekendWhenAddingWorkingDays()
- shouldRejectExecutionBeforeScheduledTime()

Не е необходимо името да описва цялата реализация. То трябва ясно да показва очакваното поведение.

*Независимост на тестовете*

Всеки unit тест трябва да може да бъде изпълнен независимо от останалите. Не трябва един тест да разчита друг тест да е изпълнен преди него; на данни, създадени от друг тест или на определен ред на изпълнение на тестовете.

Всеки тест сам подготвя необходимото начално състояние в частта Given.

*Какво трябва да се тества*

Unit тестовете трябва да проверяват публично наблюдаемото поведение, а не начина, по който то е реализирано вътрешно.

Не е необходимо директно да се тестват части методи. Те се проверяват косвено чрез поведението на публичните методи, които ги използват.

*Видове тестови сценарии*

При избора на тестови случаи трябва да се разглеждат поне три типа сценарии:

- Happy path проверява нормалното очаквано изпълнение;
- Negative path проверява ситуация, при която операцията не трябва да бъде позволена или резултатът трябва да бъде отрицателен;
- Boundary/edge case проверява стойности непосредствено около границата на дадено бизнес правило.

Граничните тестове са особено важни при бизнес правила, свързани с време, дати, максимални и минимални стойности, брой обекти, допустими срокове, проценти и ценови ограничения.

*Стартиране на unit тестове*

JUnit тестовете могат да бъдат изпълнявани директно от средата или чрез Maven.

Успешният build сам по себе си не доказва, че бизнес логиката е правилна. Това показва единствено, че всички изпълнени тестове са преминали успешно.

Следователно качеството на набора тестове зависи не само от това дали тестовете минават, а и от това дали са избрани правилните тестови сценарии.

*Mockito*

Unit тестът трябва да проверява поведението на конкретен клас независимо от останалите компоненти на приложението. Когато тествания клас има зависимости към други обекти, изпълнението на реалните им реализации може да направи теста зависим от база данни, външна система или друга бизнес логика.

За изолиране на тествания клас могат да се използват mock обекти.

Mockito е библиотека за създаване и управление на mock обекти в Java тестове.

*Реален обект и mock обект*

Обектът, чието поведение се проверява, трябва да бъде реален обект.

Ако даден service зависи примерно от repository:

```java
public class LoyaltyService {

    private final ServiceRequestRepository serviceRequestRepository;

    // ...
}
```

при unit тестването на LoyaltyService целта е да се провери неговата логика, а не работата на repository слоя. Затова в случая LoyaltyService е реалният тестван обект, а ServiceRequestRepository е mock обект.

Mock обектът замества реалната зависимост и позволява предварително да се зададе какъв резултат да върне при определено извикване.

*Създаване на mock обекти*

Mockito може да се използва със следните анотации:

```java
@Mock
private ServiceRequestRepository serviceRequestRepository;

@InjectMocks
private LoyaltyService loyaltyService;
```

Тук @Mock създава mock реализация на зависимостта, а @InjectMock създава реална инстанция на тествания клас и подава необходимите mock зависимости към нея.

За използване на Mockito анотациите с JUnit 5 тестовият клас може да бъде означен по следния начин:

```java
@ExtendWith(MockitoExtension.class)
public class LoyaltyServiceTest {

    @Mock
    private ServiceRequestRepository serviceRequestRepository;

    @InjectMocks
    private LoyaltyService loyaltyService;
}
```

Тук не се стартира Spring контекст. Mockito създава необходимите обекти за конкретния unit тест.

*Задаване на поведение на mock обект*

Поведението на mock зависимости може да бъде зададено чрез when(...).thenReturn(...). Например:

```java
when(serviceRequestRepository.countCompletedRequests(...)).thenReturn(3L);
```

Това означава, че при съответното извикване на метода repository mock-ът трябва да върне предварително зададената стойност.

Целият тест отново следва зададената структура:

```java
@Test
void shouldRecognizeLoyalCustomer() {
    // given
    String email = "customer@example.com";

    when(serviceRequestRepository.countCompletedRequests(...)).thenReturn(3L);

    // when
    boolean result = loyaltyService.isLoyal(...);

    // then
    assertTrue(result);
}
```

Настройването на mock обектите е част от Given, защото представлява подготовка на средата, необходима за изпълнението на тествания сценарий.

*Проверка на взаимодействие с mock обект*

Mockito позволява и проверка дали определен метод на mock обекта е бил извикан:

```java
verify(serviceRequestRepository).countCompletedRequests(...);
```

При необходимост може да се проверява и броят на извикванията:

```java
verify(serviceRequestRepository, times(1)).countCompletedRequests(...);
```

Методът verify() трябва да се използва когато самото взаимодействие е важно за поведението, което се проверява.

Mock-ват се зависимостите на тествания обект, а не самият обект, чието поведение трябва да бъде проверено.

Не всяка зависимост трябва да бъде mock. Прости обекти, които представляват входни данни или част от домейн модела, обикновено могат да бъдат реални:

```java
ServiceRequest request = new ServiceRequest(...);
Offer offer = new Offer(...);
```

Mock е най-подходящ за зависимости, които е необходимо да бъдат изолирани от unit теста, например:
-	repository;
-	външна услуга;
-	клиент към друга система;
-	компонент, чието реално изпълнение не е предмет на текущия тест.

Прекомерното използване на mock обекти прави тестовете трудни за четене и може да ги обвърже с вътрешната реализация на класа.

*@SpringBootTest и unit тестовете*

@SpringBootTest стартира Spring application context и е предназначен за тестове, при които е необходимо участието на Spring инфраструктурата.

@SpringBootTest се използва при интеграционни тестове, когато за проверяваното поведение е необходимо стартирането на Spring application context и съвместната работа на реални Spring компоненти.

При unit тестове Spring context не се стартира. Тестваният клас се създава директно, а зависимостите му при необходимост се заменят с mock обекти.

| Проверявано поведение                                 | Подход            |
|-------------------------------------------------------|-------------------|
| WorkingTimeService                                    | JUnit 5           |
| LoyaltyService с контролирано поведение на repository | JUnit 5 + Mockito |
| CancellationService с mock repositories               | JUnit 5 + Mockito |
| Service + реален repository + Spring context          | integration test  |
| Съвместна работа на няколко Spring компонента         | integration test  |

За зареждане на пълния Spring application context при интеграционно тестване може да се използва @SpringBootTest. Интеграционните тестове ще бъдат разгледани отделно.

### Практическа работа

За първи обект на тестване се използва WorkingTimeService. Класът съдържа бизнес логик, която не зависи от други компоненти на приложението и позволява да се разгледат основните принципи на unit тестването без използване на mock обекти.

Преди генериране на тестов код се анализират необходимите тестови сценарии.

Промпт: 

```
Analyze the existing WorkingTimeService and identify the unit test cases needed to verify its behavior.
Consider normal cases, boundary cases and invalid or exceptional cases where applicable.
For each proposed test, briefly state what behavior it verifies and the expected result.
Do not generate or modify code yet.
```

Полученото предложение да се анализира спрямо действителната реализация и бизнес правилата. Да се прецени:
-	покрити ли са всички публични операции;
-	разгледани ли са различни тестови сценарии;
-	има ли липсващи гранични стойности;
-	има ли излишни или дублиращи се сценарии;
-	предлага ли се тестване на поведение, което не е част от изискванията;
-	приема ли се случайното текущо поведение на кода за бизнес правило.

Да се оцени дали тестовите сценарии, предложени от ИИ, следват бизнес изискванията или единствено текущата реализация.

*Генериране на unit тестове*

Да се формулира промпт към ИИ асистента за създаване на unit тестове за одобрените тестови сценарии.

*Анализ на генерираните тестове*

Да се провери дали:
-	тестовете действително проверяват бизнес поведение;
-	assertions проверяват конкретен очакван резултат, а не само notNull;
-	given – when – then е използван смислено;
-	няма повторение на логиката в теста;
-	няма ненужно използване на mock обекти;
-	няма @SpringBootTest за обикновен unit тест;
-	няма опит за директно тестване на частни методи;
-	параметризираните тестове обединяват действително еднотипни сценарии;
-	всички важни гранични случаи са покрити.

При установени проблеми тестовете се коригират. При необходимост се формулира допълнителен промпт към ИИ асистента.

*Unit тест на service със зависимости*

Да се анализират зависимостите на LoyaltyService и да се определи кои обекти трябва да бъдат реални и кои могат да бъдат заменени с mock обекти. Да се определят тестови сценарии, които проверяват бизнес правилото за лоялен клиент. 

Да се разгледат нормални и гранични случаи.

Да се формулира промпт към ИИ асистента за генериране на unit тестове за избраните сценарии.

*Допълване на набора тестове*

Да се изберат поне две други бизнес правила от приложението и да се създадат подходящи тестове за тях. Възможни обекти на тестване са:
-	допустима и недопустима отмяна;
-	валиден и невалиден преход между състояния;
-	изтичане на оферта;
-	изчисляване на цена;
-	липсваща заявка;
-	гранични стойности при срокове и планиране.

*Финален анализ*

Да се използва ИИ асистента за review на създадения набор тестове. Да се формулира промпт, който да поиска анализ на качеството и пълнотата на тестовете, без промяна на съществуващия код.

Да се анализират предложенията на ИИ и да се прецени кои от тях са основателни. Да се обърне внимание на:
-	липсващи сценарии;
-	липсващи гранични случаи;
-	дублиращи се тестове;
-	прекомерно използване на mock обекти;
-	зависимост на тестовете от implementation details;
-	assertions, които не доказват очакваното поведение.

След анализа да се направят само аргументираните промени.

### Резултат

Малък и смислен набор от тестове за основни части на бизнес логиката на приложението, включващ тестове на клас без зависимости и на service с mock зависимости. Тестовете използват JUnit 5, структура given – when – then и параметризирани тестове, когато са подходящи.
