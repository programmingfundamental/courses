# Лабораторно упражнение 8

## Тестване на REST контролери

### Цел

Да се разработят автоматизирани тестове за REST контролери и да се анализира дали тестовете проверяват правилното поведението на уеб слоя.

Да се разграничат unit, controller и интеграционни тестове и да се избира подходящото ниво на тестване според поведението, което трябва да бъде проверено.

### Начално състояние

Да се използва крайната версия на приложението от ЛУ 7, съдържаща реализираната бизнес функционалност и набор от unit тестове за част от service слоя.

В приложението са реализирани REST endpoints за работа със заявки, оферти и изпълнение на услуги, Bean Validation на входните DTО обекти, специализирани изключения и единен формат на отговор при грешка.

### Кратка теория

*Различни нива на тестване*

Различните тестове проверяват различна част от поведението на приложението.

Unit тестове – проверяват отделен клас изолирано от неговите зависимости.

Контролер тестът проверява поведението на уеб слоя на приложението.

При него могат да бъдат проверени:
-	HTTP методи и URL;
-	request body;
-	преобразуване на JSON към DTO;
-	Bean Validation;
-	HTTP status code;
-	response body;
-	преобразуване на response DTO към JSON;
-	обработка на изключения;
-	единния формат на отговора при грешка.

Бизнес логиката на service слоя не е предмет на контролер теста. Зависимостите на контролера към съответните service обекти могат да бъдат заменени с mock обекти.

Интеграционният тест проверява съвместната работа на няколко реални компонента на приложението.

При необходимост от зареждане на целия Spring application context може да се използва анотацията @SpringBootTest.

*@WebMvcTest*

Анотацията се използва за тестове, фокусирани върху Spring MVC слоя. Например:

```java
@WebMvcTest(ServiceRequestController.class)
class ServiceRequestControllerTest {
    // ...
}
```

При такъв тест не е необходимо да се стартира цялото приложение. Зареждат се компонентите, необходими за тестването на уеб слоя. 

Това позволява да се провери поведението на контролера и Spring MVC инфраструктурата, без тестът да включва реалното изпълнение на всички service и repository компоненти.

*MockMvc*

Позволява изпращането на HTTP заявки към Spring MVC приложението в тестова среда, без да е необходимо стартиране на реален уеб сървър. Чрез него може да се симулира например POST /api/requests с JSON request body и да се провери полученият HTTP response.

Основната структура е:

```java
mockMvc.perform(...)
        .andExpect(...);
```

Например:

```java
mockMvc.perform(
        get("/api/requests/{id}", requestId)
    )
    .andExpect(status().isOk());
```

В контролер тестовете продължава да се използва структурата given – when – then:

```java
@Test
public void shouldReturnServiceRequest() throws Exception {
    // given
    // подготовка на данните и поведението на service dependency

    // when
    ResultActions result = mockMvc.perform(get("/api/requests/{id}", requestId));

    // then
    result.andExpect(status().isOk());
}
```

*Проверка на HTTP response*

Контролер тестът не трябва да проверява единствено дали е получен някакъв отговор. Необходимо е да се провери поведението, което е част от договора на REST API.

HTTP status, например:
- .andExpect(status().isOk())
- .andExpect(status().isCreated())
- .andExpect(status().isBadRequest())
- .andExpect(status().isNotFound())
- .andExpect(status().isConflict())

Очакваният статус трябва да съответства на конкретния API договор.

*Response body*

При JSON отговор могат да се поверяват конкретни полета:
- .andExpect(jsonPath("$.id").value(1))
- .andExpect(jsonPath("$.status").value("SUBMITTED"));

Не е достатъчно тестът да доказва единствено, че заявката е завършила успешно. Когато endpoint връща данни, трябва да се провери дали върнатите данни са правилните.

*JSON request body*

При POST и PUT операции често е необходимо Java DTO обектът да бъде преобразуван до JSON.

За тази цел може да се използва ObjectMapper.

Концептуално:

```java
String json = objectMapper.writeValueAsString(request);

//и:

mockMvc.perform(
        post("/api/requests")
            .contentType(MediaType.APPLICATION_JSON)
            .content(json)
);
```

Така тестът изпраща заявката във формат, аналогичен на използвания от REST клиента.

*Тестване на Bean Validation*

Controller тестовете позволяват да се провери дали ограниченията върху входните DTO обекти действително участват в обработването на HTTP заявката.

Например при липсващо задължително поле може да се очаква:

```java
.andExpect(status().isBadRequest());
```

При необходимост трябва да се провери и съдържанието на error response.

Това е различно от директно извикване на Java метод:

```java
controller.create(invalidRequest);
```

При директното извикване не се изпълнява автоматично целият Spring MVC процес на десериализация и валидация на HTTP request.

*Тестване на обработката на грешки*

В приложението бизнес грешките се представят чрез специализирани exceptions и се преобразуват до HTTP response от общия exception handler.

При controller тест service dependency може да бъде конфигурирана да хвърли съответния exception.

Например концептуално:

```java
when(service.someOperation(...))
        .thenThrow(new RequestNotFoundException(...));
```

След изпращане на HTTP заявката трябва да се провери дали web слоят преобразува грешката до правилния:
•	HTTP status; 
•	error response; 
•	формат на JSON отговора. 

По този начин controller тестът не проверява защо service-ът е решил, че заявката не съществува. Това е предмет на unit тест на service слоя.

#### Какво не трябва да проверява controller тестът

Controller тестът не трябва да повтаря unit тестовете на бизнес слоя.

Например controller тестът не трябва повторно да доказва:
•	как се изчислява цената; 
•	как се определя лоялен клиент; 
•	как се изчисляват работните дни; 
•	защо дадена отмяна е разрешена; 
•	как се изпълнява конкретен status transition. 

Тези правила трябва да бъдат проверени чрез unit тестове на съответните класове.

Controller тестът проверява HTTP поведението, чрез което тази функционалност е достъпна.

### Практически задачи

*Анализ на ServiceRequestController*

Като първи обект за тестване да се използва ServiceRequestController. Преди генериране на тестов код да се анализират необходимите тестови сценарии за контролера.

Промпт:

```
Analyze the existing ServiceRequestController and identify the controller test cases needed to verify its HTTP behavior.
Consider successful requests, request validation, business errors, HTTP status codes and response bodies.
Distinguish what should be tested at the controller/web layer from behavior that belongs to service unit tests.
Do not generate or modify code yet.
```

Получените предложения да се сравнят с реалната имплементация на контролера и съществуващия API договор. Да се прецени:
-	обхванати ли са всички REST операции;
-	правилни ли са предложените HTTP статус кодове;
-	проверява ли се response body;
-	разгледани ли са невалидни заявки;
-	разгледани ли са бизнес грешките, които контролера може да получи от service слоя;
-	предложени ли са сценарии, които всъщност принадлежат на service unit тестове;
-	предложени ли са сценарии, които не съществуват в текущите изисквания.

*Генериране на контролер тестове*

След одобряване на тестовите сценарии да се формулира промпт към ИИ асистента за създаване на контролер тестове.

*Анализ на генерираните тестове*

Генерираните тестове да се изпълнят и анализират. Да се провери дали ИИ асистентът:
-	използва подходящ тип тест;
-	използва @SpringBootTest без необходимост;
-	стартира или създава реални зависимости между сървиси;
-	mock-ва самия контролер;
-	проверява единствено HTTP status;
-	проверява response body когато даден endpoint връща данни;
-	използва правилните HTTP status codes;
-	проверява Bean Validation;
-	проверява стандартизирания отговор при грешка;
-	дублира бизнес логиката от unit тестовете;
-	създава прекалено много mock обекти;
-	добавя тестове за несъществуващо поведение.

При установени проблеми да се направят необходимите корекции.

*Разширяване на набора от контролер тестове*

След анализа на първите генерирани тестове да се изберат REST операции от останалите контролери.

Подходящи сценарии могат да бъдат:
-	успешно създаване на оферта;
-	опит за създаване на оферта при недопустимо състояние на заявката;
-	приемане на валидна оферта;
-	операция върху изтекла оферта;
-	успешно планиране на изпълнение;
-	невалидна дата за планиране;
-	стартиране на изпълнение;
-	опит за недопустима отмяна;
-	заявка към несъществуващ ресурс.

Да се изберат няколко сценария, които проверяват различни аспекти на HTTP поведението, а не множество варианти на една и съща операция.

За избраните сценарии:
-	да се определи очакваното HTTP поведение;
-	да се формулира промпт;
-	да се анализира генерирания код;
-	да се изпълнят тестовете;
-	да се коригират установените проблеми.

### Сравнение на нивата на тестове

За един избран бизнес сценарий да се определи какво би било проверено на различните нива. 

Например при отказ на недопустима операция:
-	unit тест на service – правилно ли разписаната логика разпознава недопустимата операция и хвърля съответното изключение;
-	контролер тест – преобразува ли REST контролера това изключение до 409 грешка и правилния отговор;
-	интеграционен тест – работи ли целия сценарий правилно при съвместно изпълнение на реалните компоненти.

Не е необходимо един и същ сценарий винаги да се реализира на всички нива. Целта е да се избере нивото, което проверява интересуващото поведение с възможно най-малък ненужен обхват.

*Финален анализ с ИИ*

Да се използва ИИ асистентът за анализ на създадения набор от контролер тестове.

Да се потърсят:
-	непокрити REST операции;
-	липсващи негативни сценарии;
-	липсващи проверки за response body;
-	неправилни HTTP очаквания;
-	дублиране с unit тестове;
-	ненужно използване на @SpringBootTest;
-	прекомерно използване на mock обекти;
-	тестове, зависими от конкретна реализация;
-	тестове, които преминават успешно, без реално да доказват API договор.

Получените предложения да се оценят и да се приложат само аргументираните промени.

### Резултат

Набор от автоматизирани тестове за избрани REST операции, който проверява:
-	успешни HTTP заявки;
-	Bean Validation;
-	HTTP status codes;
-	JSON response;
-	обработка на бизнес грешки;
-	единен отговор при грешка.

Тестовете използват подходящо ниво на изолация и не стартират ненужно целия Spring application context.
