# Упражнение 5 — Ограничаване на опитите за вход — решения и насоки


## Решение на примерния проблем

LoginAttemptService е @Service с Clock, max, duration и reset. Използваме synchronized методи за достъп до bounded Map<String,State>, където State съдържа failures, until. За даден username:

1. Преди операция премахваме state, когато now>=until.
2. blocked връща failures>=max. Ако map е пълна с активни записи и името е ново, отказваме временно, вместо да разрешим обход.
3. failure създава count=1 или увеличава count. До достигане на max обновява until=now+duration; при вече блокиран state не променя срока.
4. success премахва state само при reset=true. Не предоставяме HTTP операция за зануляване на глобалната map.

В AuthService преди authenticate: ако attempts.blocked(username), хвърляме общ 401. В catch(AuthenticationException) извикваме attempts.failure(username) и връщаме същия 401. След успешен authenticate извикваме attempts.success(username). Промените по session/token са след този резултат. Не държим заключване на map по време на BCrypt.

## Решение на самостоятелна задача 1

Настройките се инжектират с @Value; max<1 или duration<=0 хвърля IllegalArgumentException в конструктора. За конфигурация A задаваме max-attempts=3, lock-duration=PT30S, reset-after-success=false; за B — 5/PT60S/true. След всяка промяна рестартираме приложението и изпращаме login заявките ръчно с Postman.

Конфигурация A: failure → success(200) → failure → failure → правилна парола(401). Изчакваме 30 секунди от блокировката → 200. Конфигурация B: четири failures → success(200) → още четири failures → success(200). Пет failures блокират до изтичане на 60 секунди. Bob остава 200. При max=0, PT0S и отрицателен срок стартираме с всяка конфигурация и проверяваме отказа в логовете; после възстановяваме валидните настройки. Ръчната проверка не доказва точната времева граница.

## Решение на самостоятелна задача 2

Две конкурентни failure операции след max−2 довеждат до blocked=true; synchronized предотвратява загуба. Ръчна проверка с capacity+1 имена проверява, че размерът не расте и новият опит се отказва до освобождаване. При NAT account броячите остават отделни; общият IP лимит има по-висок праг. Рестарт губи map — проверяваме с нова инстанция; устойчивостта изисква общо хранилище. За истинско ограничение на паралелни BCrypt операции е необходим отделен ограничител на едновременните заявки; броячът сам не осигурява това.
