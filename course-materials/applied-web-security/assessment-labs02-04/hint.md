# Преподавателски бележки за практическото контролно

## Обхват и източници

Контролното адаптира въпрос 5 от `../lab02-threat-modeling/web-security-lab02-ms-forms.docx`, въпроси 1 и 4 от `../lab03-authentication/web-security-lab03-ms-forms.docx` и въпроси 3 и 7 от `../lab04-authorization/web-security-lab04-ms-forms.docx`. Не се изисква Java редакция от студента: изводите се правят от реални HTTP заявки и състояние на H2. Показаният код не претендира да е завършеното решение на базовия Task Manager.

Проектът е Java 17, Spring Boot 3.5.7, JDBC/H2 и BCrypt. Сървърът поддържа отделна cookie сесия за всяка проверка и участник. Идентификаторите и opaque access/refresh tokens се пазят хеширани в H2; access token може да удостовери API заявка в същата проверка и работно място. Панелът използва само cookies. Няма JWT, refresh endpoint или Spring Security filter chain: тези механизми не са предмет на избраните въпроси. Logout отменя и двата вида tokens; поведението не моделира неизтекъл JWT от въпрос 7 на тест 3.

## Подготовка и провеждане

Препоръчително време: 60–75 минути, включително подготовката. Осигурете Java 17+ и изпробвайте пакета на студентска машина. Първото Maven/Docker изграждане изисква мрежа; готовият JAR пакет работи без изтегляне на зависимости.

Всеки браузърен профил получава случайно работно място с независими копия на петте набора данни. Не използвайте един браузърен профил за няколко студенти. При централен сървър всички участници трябва да достъпват един и същ адрес последователно; localhost и 127.0.0.1 имат различни cookies. По подразбиране слушането е на loopback. За изолирана учебна LAN може да се зададе HOST=0.0.0.0 и да се разреши съответният порт. При Docker промяната е в host bind на ports. Два сценария умишлено нарушават политики; използвайте само синтетичните данни и изолирана учебна среда.

Не се изискват отговори чрез преглед на сървърния код. Дайте готовия студентски ZIP или достъп до стартиран сървър. Изходният код и байткодът могат да разкрият поведението; пакетът не е средство за пазене на поверителни изпитни материали. Системата не удостоверява реалната самоличност на студента и няма централен прием на предавания. JSON се предава през избрания учебен канал. Записите са генерирани на сървъра, но изтегленият файл може да бъде редактиран — не е подписано доказателство или защитена изпитна платформа.

Нулирането засяга само избраната проверка. Отговорите и доказателствата остават, а generation се увеличава. Оценявайте конкретния номер на опита. При работа в няколко таба редакциите на отговорите са „последният запис печели“; препоръчайте един таб. Cookie за работното място е валидно 30 дни, сесиите — 8 часа. Рестартът запазва H2 данните и валидните сесии. Срокът не се удължава автоматично.

## Ключ и очаквани наблюдения

| Проверка | Очаквано поведение | Извод |
| --- | --- | --- |
| 1 | Регистрация с role=ADMIN → 200; вход; /auth/me и /diagnostics/users/candidate → USER; отчет → 403. | Полето от клиента не определя ролята. Успешната регистрация сама не доказва записаната роля. Диагностиката прави SELECT от H2 само за текущия профил. |
| 2 | Alice влиза; login за Bob с грешна парола в същата удостоверена сесия → 200, ново обозначение и tokens за Alice; /auth/me → Alice. Същата грешна парола след logout → 401 без tokens. | Ранното връщане при вече удостоверена сесия заобикаля проверката на новите credentials. Смяната на session ID не поправя липсващата проверка. |
| 3 | Alice → успешен login като Bob; 200; различно обозначение на сесията; следващото /auth/me → Bob. | Трите условия са изпълнени. Login JSON сам по себе си не доказва самоличността в следващата заявка. Старото cookie вече не удостоверява. |
| 4 | Bob PATCH на задача 101 → 404, но следващият GET като Alice показва променено summary. Owner и description са запазени, ако не са подадени други полета. | Отказът е след записа и не гарантира непроменени данни. Обектната проверка трябва да предхожда промяната; HTTP кодът не е доказателство за липса на странични ефекти. |
| 5 | Alice: задача 200, отчет 403; Bob: задача 404, липсваща задача 404 със същото тяло, отчет 403; Admin: задача и отчет 200. | Собствеността и ролята са различни правила. Достъпът до задачата не отменя ADMIN-only правилото за отчет. Еднакъв 404 не доказва липса на времеви/други канали. |

Проверки 2 и 4 съдържат преднамерени дефекти в `ApiController.route`; останалите реализират описания договор. Те са ограничени с `caseNo` и `workspace` във всички SQL заявки. Не „поправяйте“ двата дефекта, когато пакетът се използва за това контролно. Съответните интеграционни тестове потвърждават точно тези наблюдения.

## Оценяване

Всяка проверка носи до 20 точки: 5 за възпроизводими действия и правилна самоличност; 7 за релевантни доказателства (включително проверка след операцията, когато е нужна); 8 за верен и ограничен до наблюденията извод. Общо 100. Попълненият текст в интерфейса означава само наличие на отговор, не автоматична оценка или правилност.

## Поддръжка, синхронизация и проверки

Студентското съдържание се редактира в `content/assignment.json`, после:

```powershell
java tools/SyncContent.java
java tools/SyncContent.java --check
.\mvnw.cmd clean verify
java tools/PackageStudent.java
java tools/PackageProject.java
```

Синхронизацията обновява единствено `src/main/resources/static/assignment.json`. Интеграционният тест сравнява източника и копието. Проектът е отделно приложение; не е добавен нов номер на упражнение и не се публикува автоматично от Astro синхронизацията. Използва се само allowlist на статичните ресурси; Spring static mappings и H2 Console са изключени.

Готовият пакет е `target/web-security-assessment-student.zip`: изпълним JAR, студентски README и скриптове за стартиране. Пакетиращият инструмент отхвърля JAR с hint.md или интеграционния тест. Този файл, тестовете и данните от `data/` не се включват в студентския пакет и не се сервират през HTTP. Docker копира само runtime изходните файлове и не публикува H2 порт.

Тестовете проверяват петте сценария, изолация между участници и проверки, отмяна на сесии и tokens, reset с история, редактиране на отговори, скриване на credentials в дневника, ограниченията на входа, origin проверка, непубликуване на преподавателски файлове, синхронизацията и H2 съхранението след затваряне и повторно отваряне на файл.

За справка: [H2 файлов режим](https://h2database.com/html/features.html#database_url) и [Spring Boot 3.5 изисквания](https://docs.spring.io/spring-boot/3.5/system-requirements.html).
