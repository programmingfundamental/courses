# Упражнение 7 — Интеграция на AI компонент — Git и CI/CD

## Теория

### Работа в Scrum: интеграция и общо качество

AI инженерът превръща командите за данни, модел и оценка в повторяеми проверки. С останалите Developers договаря обща DoD: промяна в Python не е завършена, ако нарушава Java договора. Sprint Backlog съдържа конкретни зависимости между проверките и пакетиране. За Review демонстрира успешен прогон и контролиран провал, който блокира кандидат за модел. При Retrospective разглежда причината за най-честите CI провали и избира едно подобрение, например детерминистичен fixture вместо зависимост от стар работен файл.

### 1. Версии и съвместна работа

1. **Commit и клон.** Commit е проверим набор промени; клонът изолира работа. Commit съобщението обяснява поведението и причината, а не само списък файлове.
2. **Pull request и review.** Прегледът проверява изискванията, рисковете, тестовете и документацията. Зелен pipeline не заменя преглед на бизнес правилата.
   - **Пример:** тестовете минават, но предложението за категория вече се записва автоматично — това противоречи на SRS.
3. **Конфликт.** Две текстови промени може да се слеят успешно и да остане логически конфликт. След merge се проверяват код, API договор и UML модел.

### 2. CI/CD и quality gates

**Continuous Integration** проверява интеграцията при промяна. **Continuous Delivery** подготвя проверен артефакт за внедряване; **Continuous Deployment** го внедрява автоматично. За учебния проект външно публикуване не е необходимо; достатъчна е възпроизводима локална среда.

Pipeline има зависимости: Java тестове и Python проверки → integration сценарий → пакетиране. Провалът на която и да е задължителна проверка блокира следващия етап. Gate върху macro-F1 използва реалния отчет от тема 6, а не подставена стойност.

### 3. Среда, кеш и артефакти

1. **Възпроизводимост.** Записваме Java/Python версии, зависимости, конфигурация и идентичност на данните. Maven Wrapper фиксира Maven, а Python lock файлът — пакетите.
2. **Кеш и артефакт.** Кешът ускорява зависимостите; артефактът е резултат от конкретното изпълнение. Стар отчет от кеша не доказва текущ успех.
3. **Secrets.** Пароли и signing ключове се подават чрез локална среда или CI secrets. Не се записват в YAML, диаграми или логове.


### Прилагане в Task Manager


На единия компютър Task Manager работи, а на другия Python услугата използва различна версия на библиотеките. Тестовете минават само ако остане база от предишно стартиране.

#### Стъпка 1. Фиксиране на входовете

Продължете [тема 6](../week06-testing/lab06.md). Запишете команди за чисто изпълнение на Java и Python тестовете, инсталиране от lock файла и обучение с фиксираните данни. Всеки тест създава и почиства собствените си данни. Добавете командите в README на студентското решение.

#### Стъпка 2. Контейнеризация на AI услугата

Добавете Dockerfile в `ai-service`, който инсталира фиксираните зависимости и стартира избрания WSGI сървър, слушащ на порт 8000. Добавете и него в lock файла. Не използвайте development/debug режим. Добавете Compose услуга `category` на backend мрежата и read-only mount за обучен артефакт. Spring използва конфигурируем URL `http://category:8000`; този вътрешен порт няма нужда от публикация към хоста.

#### Стъпка 3. Подреждане на проверките

Опишете pipeline в `.github/workflows/ci.yml` или друга избрана CI система. Java и Python проверките могат да са независими, но пакетиране има зависимост от двете. Използвайте `./mvnw verify` за Java, а за Python — собствените команди за валидация на данни, обучение и тестове. Докажете, че всяка команда връща ненулев exit code при провал.

Примерна логическа последователност, която трябва да реализирате с действителните имена на файловете:

```text
checkout → Java tests ───────────┐
         → Python/data/ML tests ├→ isolated E2E → image build → reports
                               ┘
```

#### Стъпка 4. Проверка на чиста среда

Използвайте отделен Compose проект `se-task-manager-ci`, отделна тестова конфигурация и свободен порт, например 19001. Всички start/log/stop команди за този прогон използват това име. След readiness проверките изпълнете E2E сценария. Почистването се изпълнява и при провал; унищожават се само тестови данни, не работният volume `se-task-manager`.

#### Стъпка 5. Доказване на блокиране

Направете временна промяна, която нарушава теста за предложение без запис. Запазете неуспешния CI резултат и покажете, че няма нов успешно публикуван артефакт за този commit. Възстановете кода и запазете успешния прогон. Deployment диаграмата се актуализира според действителните услуги и мрежи.


## Примерен проблем

Pipeline допуска модел, защото файлът с метрики съществува, въпреки че липсва оценка за един клас. AI инженерът трябва да направи проверката изпълнима и блокираща преди пакетиране.

### Решение

Запишете `ai-service/ml_gate.py`:

```python
import json
import math
import sys
from pathlib import Path

LABELS = ("BUG", "FEATURE", "DOCUMENTATION")

def check_report(report):
    for label in LABELS:
        support = report.get(label, {}).get("support", 0)
        if not isinstance(support, (int, float)) or isinstance(support, bool):
            raise ValueError("Invalid support: " + label)
        if not math.isfinite(support) or support <= 0:
            raise ValueError("Missing support: " + label)
    score = report.get("macro avg", {}).get("f1-score")
    if not isinstance(score, (int, float)) or isinstance(score, bool):
        raise ValueError("Invalid macro-F1")
    if not math.isfinite(score) or not 0.70 <= score <= 1:
        raise ValueError("ML-01 failed")

if __name__ == "__main__":
    try:
        check_report(json.loads(Path(sys.argv[1]).read_text(encoding="utf-8")))
    except (OSError, ValueError, KeyError, TypeError, AttributeError, IndexError) as error:
        print("BLOCK:", error, file=sys.stderr)
        sys.exit(1)
    print("PASS: class support and ML-01")
```

Gate проверява структура и праг. Произходът, достатъчността на извадката и честната оценка се проверяват отделно; валиден JSON не ги доказва. Етапът за обучение трябва да приключи успешно преди четене на отчета, за да не се приеме стар файл.

### Проверка на резултата

Изпълнете `python ml_gate.py reports/evaluation.json` след действително обучение. Отчетът от пример 6 е подходящ за проверка на механизма, но не доказва достатъчност на данните за задачите. При покрити условия изходът е `PASS: class support and ML-01`, exit code 0; при липсващ файл, липсващ support, NaN или F1 под 0.70 — `BLOCK` и exit code 1. Изтрийте DOCUMENTATION само в копие на отчета и проверете отказа; не редактирайте действителния ML отчет, за да получите успех.


### Свързване с CI

В работното хранилище с папки `task-manager` и `ai-service` следният завършен job стартира Python проверките, реалното обучение и gate преди пакетиране на кандидат. Предпоставки: `train.py`, `tests/`, `data/` и lock файлът са реализирани по упражнение 6; lock файлът включва pytest. Изходите са `reports/evaluation.json` и `artifacts/model.joblib`, както в ядрото за обучение от упражнение 6.

```yaml
name: AI candidate
on: [push, pull_request]
jobs:
  candidate:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: ai-service
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: python -m pip install -r requirements.lock.txt
      - run: python -m pytest
      - run: python train.py
      - run: python ml_gate.py reports/evaluation.json
      - run: tar -czf candidate.tgz artifacts/model.joblib reports/evaluation.json requirements.lock.txt
```

По подразбиране провален step спира следващите. Това е пакетиране на AI кандидат; публикуване на общия продукт изисква и Java и E2E проверките от задачите. Запишете YAML в `.github/workflows/ai-candidate.yml`. Локалното изпълнение на същите Python команди проверява логиката, но не е доказателство за проведен външен CI прогон.


## Самостоятелни задачи

### Задача 1. CI за AI инженера

Автоматизирайте инсталиране от lock файл, валидиране на данни, Python тестове, реално обучение, ML gate и пакетиране. Кандидатът трябва да носи точния commit, отчет и версия; добавете зависимост от Java и изолиран E2E тест преди приемане на общата версия. Предайте YAML, локални команди и действителен статус. При липса на външен CI достъп запишете този прогон като непроверен.

### Задача 2. Договор при промяна

Направете отделен клон за промяна в модела или payload. Прегледайте с backend частта съвместимостта на category и modelVersion. Възпроизведете конфликт между код и договор и го разрешете; актуализирайте Mermaid Deployment и Sequence моделите. Предайте diff, `.mmd`, SVG, аргументи от review и проверката, която открива логическото несъответствие.

### Задача 3. Доказано блокиране

Покажете отделно провален тест, липсващ клас и липсващ модел. При всеки случай не трябва да има приет нов кандидат и стар отчет не трябва да замества текущото изпълнение. Докажете отделна тестова база и запазена работна среда. Предайте логове без secrets и промяна в DoD/плана за спринта, основана на намерения пропуск.
