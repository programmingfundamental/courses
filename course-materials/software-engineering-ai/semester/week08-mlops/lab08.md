# Упражнение 8 — Внедряване на AI модели — MLOps и версии

## Теория

### Работа в Scrum: внедряване на проверим модел

AI инженерът предлага кандидат за версия, проследява произхода и сравнява качеството с активния модел. Решението в Sprint Backlog е конкретно: публикуване само при изпълнени критерии, иначе запазване на предишния модел и нова работа за недостатъка. За Review показва потребителско предложение с действителна версия и rollback. При Retrospective анализира дали възстановяването зависи от ръчна недокументирана стъпка. Краят на Sprint не задължава екипа да активира модел с влошено качество.

**Model card** описва предназначение, данни, класове, измерени резултати, ограничения и неподдържани случаи. AI инженерът включва такава информация към версията, за да може екипът да реши дали тя е подходяща за текущите потребители.

### 1. Жизнен цикъл на модела

MLOps организира данните, обучението, оценяването, публикуването, използването и наблюдението на модели. В Task Manager моделът е един компонент; останалото приложение има собствен жизнен цикъл.

1. **Версия на данни.** ID и checksum идентифицират конкретните файлове. Само име `latest.csv` не гарантира еднакъв вход.
2. **Експеримент.** Записва код, данни, настройки, среда, метрики и резултат. Seed е необходим при случайни операции, но сам по себе си не фиксира цялата среда.
3. **Артефакт.** Обученият pipeline съдържа преобразуването на текста и модела. Отделно променен речник може да направи модела несъвместим.

### 2. Оценяване и избор

Сравняваме модели по еднакъв протокол: същата оценъчна извадка, класове, метрики, среда и измерване на latency. Не избираме версия само по обща accuracy. Измерваме macro-F1, recall и support по класове, p95 и размер на артефакта. Многократно настройване по една и съща оценъчна извадка може да доведе до свръхнапасване към нея; записваме това ограничение.

**Пример:** v2 подобрява BUG, но влошава DOCUMENTATION под приемливия минимум. Решението за публикуване трябва да отчете това, дори средната метрика да е по-висока.

### 3. Публикуване и rollback

Моделните версии са неизменяеми. `active.json` сочи избраната версия; смяната се прави едва след проверка на артефакта и средата. Rollback връща предишна доказано зареждаема версия. Метаданните не трябва да твърдят v1, когато в паметта е v2.

```json
{
  "modelVersion": "v1",
  "codeCommit": "<actual-commit>",
  "trainSha256": "<actual-sha256>",
  "evaluationSha256": "<actual-sha256>",
  "lockSha256": "<actual-sha256>",
  "artifactSha256": "<actual-sha256>",
  "labels": ["BUG", "FEATURE", "DOCUMENTATION"],
  "report": "evaluation.json"
}
```

Полетата с `<...>` се попълват с действителни стойности. Шаблонът не е готов протокол за изпълнение.


### Прилагане в Task Manager


Екипът има по-добър модел v2, но файлът `model.joblib` е презаписан и не е ясно с кои данни е обучен. Трябва да публикуваме проверима версия и да можем да се върнем към v1.

#### Стъпка 1. Версиониране на работната основа

Продължете [pipeline от тема 7](../week07-cicd/lab07.md). Запазете текущия обучен модел от тема 6 като v1 заедно с отчета и действителните входове. Ако произходът не може да се възстанови, обучете наново и обозначете новата версия; не измисляйте липсващи метаданни.

#### Стъпка 2. Неизменяем пакет

Променете командата за обучение да приема версия. Пишете във временна директория, проверявайте всички файлове и публикувайте като `artifacts/v1/` само при успех. При съществуваща версия откажете презаписване. Пакетът съдържа модел, metadata.json и evaluation.json. SHA-256 на самия модел се записва след сериализацията.

#### Стъпка 3. Кандидат v2

Обучете v2 с обоснована промяна — например character n-grams или различна регуляризация. Запазете същите train/evaluation разделения за сравнение на алгоритми. Ако сравнявате и промяна на данните, означете това като отделен експеримент. Измерете моделите с еднакъв warmup, брой заявки и concurrency.

#### Стъпка 4. Контролирано активиране

Проверете schema, checksum, допустими класове, lock файл и ML-01 преди активиране. За учебната система използвайте един оператор, атомична подмяна на указателя и контролиран рестарт на category услугата; не е необходимо hot reload. След рестарта `/health` и `/suggest` трябва да отразяват действително заредения модел. При неуспех върнете предишния указател и рестартирайте с него.

#### Стъпка 5. Rollback с доказателства

Активирайте v2, изпратете реална заявка през Task Manager и запазете modelVersion. Върнете v1, повторете заявката и проверете v1. Уверете се, че потвърдените категории на задачите не се променят. Използвайте Activity модела от упражнение 3 за последователността, а Deployment — за местоположението на артефакта.


## Примерен проблем

Кандидат с повреден артефакт не бива да заменя активния модел. Ще реализираме проверка на идентичност и атомична смяна на указателя, включително връщане към предишна версия.

### Решение

Запишете `activation_demo.py`:

```python
from pathlib import Path
import hashlib
import json
import tempfile

def activate(root, version):
    if version not in ("v1", "v2"):
        raise ValueError("Unknown version")
    package = root / version
    metadata = json.loads((package / "metadata.json").read_text(encoding="utf-8"))
    digest = hashlib.sha256((package / "model.bin").read_bytes()).hexdigest()
    if metadata["modelVersion"] != version or metadata["artifactSha256"] != digest:
        raise ValueError("Artifact identity mismatch")
    candidate = root / "active.tmp"
    candidate.write_text(json.dumps({"modelVersion": version}), encoding="utf-8")
    candidate.replace(root / "active.json")

def active(root):
    return json.loads((root / "active.json").read_text(encoding="utf-8"))["modelVersion"]

with tempfile.TemporaryDirectory() as directory:
    root = Path(directory)
    for version in ("v1", "v2"):
        package = root / version
        package.mkdir()
        payload = ("synthetic artifact " + version).encode()
        (package / "model.bin").write_bytes(payload)
        (package / "metadata.json").write_text(json.dumps({
            "modelVersion": version,
            "artifactSha256": hashlib.sha256(payload).hexdigest(),
        }), encoding="utf-8")
    activate(root, "v1")
    activate(root, "v2")
    assert active(root) == "v2"
    activate(root, "v1")
    (root / "v2/model.bin").write_bytes(b"corrupted")
    try:
        activate(root, "v2")
    except ValueError:
        assert active(root) == "v1"
    else:
        raise AssertionError("Corrupted artifact accepted")
    print("PASS: activation, rollback, rejected corruption; active=v1")
```

Синтетичните байтове проверяват управлението на файловете; не са обучен модел. При интеграцията добавете проверките на реалния артефакт, ML отчета и средата преди смяната. Един оператор извършва активацията; конкурентни процеси изискват допълнителна координация. След смяна рестартирайте AI услугата и проверете `/health` и `/suggest`: активният указател сам не доказва коя версия е в паметта.

### Проверка на резултата

Изпълнете `python activation_demo.py`. Очаквайте `PASS: activation, rollback, rejected corruption; active=v1`. Примерът създава и почиства собствена временна директория. Провалът преди `replace` оставя active.json непроменен.
