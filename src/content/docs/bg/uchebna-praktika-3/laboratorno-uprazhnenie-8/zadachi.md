### Избор на функционалност за тестване

Да се използва service-ът, избран за unit тестване в ЛУ 7, и да се установи чрез кои REST операции неговата функционалност е достъпна от web слоя.

Да се избере една REST операция, свързана с вече тествано бизнес поведение.

За избраната операция да се определят:

•	controller-ът и endpoint-ът;

•	HTTP методът;

•	използваните request и response DTO обекти;

•	приложимите правила за Bean Validation;

•	очакваните HTTP status кодове;

•	възможните грешки от service слоя и начинът, по който се представят като HTTP response.

### Определяне на необходимия контекст според нивото на теста

За избраната функционалност да се сравни контекстът, необходим за unit тестването ѝ в ЛУ 7, с контекста, необходим за проверка на свързаното REST поведение.

Да се определи:

•	коя информация от предишния контекст остава релевантна;

•	коя вече не е необходима за controller теста;

•	какъв нов контекст е необходим за проверка на web слоя;

•	кои зависимости трябва да бъдат реални и кои да бъдат заменени с mock обекти;

•	кои проверки принадлежат на controller теста и не трябва да дублират вече проверена бизнес логика.

На базата на анализа самостоятелно да се подбере project context за работата с ИИ асистента. Чрез прикачване да се добавят само файловете, релевантни за конкретното поведение и избраното ниво на теста.

При установен липсващ контекст да се определи каква информация е необходима и да се добавят само съответните файлове.

### Проверка на тестовата конфигурация

Да се провери дали текущата тестова конфигурация на проекта поддържа необходимите средства за controller тестване – @WebMvcTest, MockMvc, Mockito и работа с JSON.

Необходимите библиотеки могат вече да бъдат предоставени от съществуващите Spring Boot test dependencies. Ако зависимост действително липсва, да се направи само необходимата промяна и Maven проектът да се презареди.

Предложения за промени в pom.xml да не се приемат автоматично, без проверка на текущата конфигурация.

### Генериране и проверка на controller тестове

Самостоятелно да се организира работата с ИИ асистента за определяне на подходящи controller test сценарии и генериране на необходимите тестове. Да се използва подбраният за задачата project context и при необходимост той да се допълва в хода на работата.

Преди прилагане на генерираните тестове да се провери дали:

•	проверяват действителните HTTP method и URL;

•	request данните съответстват на реалните DTO обекти;

•	очакваните HTTP status кодове и response body съответстват на API договора;

•	Bean Validation и error response се проверяват в приложимите сценарии;

•	service зависимостите са изолирани подходящо;

•	не се дублира бизнес логика, която принадлежи на unit тестовете;

•	не се използва ненужно @SpringBootTest;

•	ИИ не е добавил несъществуващо API поведение.

Одобрените тестове да се добавят към проекта и да се изпълнят.

При установено несъответствие да се приложи процесът за root-cause analysis и да се определи дали причината е в генерирания тест, предоставения контекст, очакваното HTTP поведение, тестовата конфигурация или реализацията на web слоя.

Да се коригира установената причина, без автоматично регенериране на целия тест или промяна на реализацията единствено с цел тестът да премине успешно.

### Разширяване на набора от controller тестове

След проверка на първоначално избраната REST операция да се реализират controller тестове за още няколко сценария от съществуващия REST API, включващи различни аспекти на поведението на web слоя, например:

•	успешно изпълнение на операция;

•	невалидни входни данни;

•	преобразуване на грешка от service слоя до съответния HTTP response.

За всеки сценарий самостоятелно да се определят проверяваното поведение, необходимият project context и зависимостите, които трябва да бъдат изолирани.

Самостоятелно да се организира работата с ИИ асистента, да се генерират необходимите тестове и да се извърши тяхната проверка и изпълнение.

При установен проблем да се анализира причината и да се коригира конкретното несъответствие. Ако за диагностиката е необходим допълнителен project context, да се добавят само необходимите файлове.

### Финална проверка

След приключване на работата да се провери дали:

•	за всеки тест е ясно какво поведение проверява и защо принадлежи на controller ниво;

•	използваният project context е релевантен за конкретната задача;

•	HTTP method, URL, request данните, status кодовете и response body съответстват на действителния API договор;

•	service зависимостите са изолирани подходящо и controller тестовете не дублират unit тестването на бизнес логиката;

•	генерираните тестове са прегледани и изпълнени, а при установено несъответствие е проверена причината преди извършване на корекция.
