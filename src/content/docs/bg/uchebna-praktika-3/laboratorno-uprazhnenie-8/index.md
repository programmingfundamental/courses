# Лабораторно упражнение 8

## Избор на контекст според задачата и нивото на теста

### Цел

Целта на упражнението е да се изследва как задачата и избраното ниво на тестване определят контекста, необходим при работа с ИИ асистент за генериране на автоматизирани тестове.

Чрез преминаване от unit тестване на избрана бизнес функционалност към тестване на съответното REST поведение ще бъде анализирано коя информация е релевантна за различните нива на теста и коя не е необходима за конкретната проверка.

Практическата работа е насочена към преминаване от unit към controller тестване и проверка на генерираните тестове спрямо действителния API договор, текущата реализация и резултатите от тяхното изпълнение.

### Различни нива на тестване

Различните нива на тестване проверяват различен обхват от поведението на приложението.

*Unit* тестът проверява изолирано поведението на отделен клас. Тестваният клас се създава директно, а неговите зависимости при необходимост се заменят с mock обекти.

*Controller* тестът проверява поведението на web слоя. При него могат да бъдат проверени HTTP методът и URL, обработката на request body, Bean Validation, HTTP status, response body и преобразуването на възникнали грешки до съответния HTTP response. Бизнес логиката на service слоя не е предмет на controller теста.

*Integration* тестът проверява съвместната работа на няколко реални компонента на приложението и при необходимост може да включва Spring application context.

Изборът на ниво на теста се определя от поведението, което трябва да бъде проверено. По-големият обхват не означава автоматично по-добър тест.

### Избор на контекст според проблема и нивото на теста

Контекстът, необходим на ИИ асистента за генериране на тестове, зависи не само от функционалността, която се тества, но и от нивото, на което тя трябва да бъде проверена.

При unit тест на service могат да бъдат релевантни кодът на тествания клас, неговите зависимости и бизнес правилата, които определят очакваното поведение.

При controller тест за свързана функционалност фокусът се променя. Релевантни могат да бъдат REST endpoint-ът, HTTP методът, request и response DTO обектите, правилата за валидация, HTTP status кодовете, форматът на грешките и поведението, което controller очаква от service слоя. Вътрешната реализация на бизнес логиката обикновено не е необходима, когато тя не е предмет на текущия тест.

При integration тест е необходим по-широк контекст, защото се проверява взаимодействието между реални компоненти.

Следователно *релевантният контекст не е фиксиран набор от файлове или информация*. Той се определя от въпроса, на който конкретният тест трябва да отговори. Предоставянето на повече контекст не е самоцел – ненужната информация може да разшири задачата и да насочи ИИ към поведение, което не принадлежи на избраното ниво на тестване.

### Controller тестове със Spring MVC

За тестове, фокусирани върху Spring MVC слоя, може да се използва @WebMvcTest. При такъв тест се зареждат компонентите, необходими за проверка на web слоя, без да е необходимо да се стартира цялото приложение.

MockMvc позволява да бъдат изпращани HTTP заявки към Spring MVC приложението в тестова среда, без стартиране на реален web server. Чрез него могат да бъдат проверени:

•	HTTP status;

•	съдържанието на JSON response;

•	обработката на request body;

•	Bean Validation;

•	преобразуването на exceptions до съответния HTTP response.

Зависимостите на controller към service слоя могат да бъдат заменени с mock обекти. Така controller тестът проверява как web слоят реагира на определен резултат или грешка от service слоя, без повторно да проверява самата бизнес логика.

За работа с JSON request body може да се използва ObjectMapper, а съдържанието на JSON response може да бъде проверено чрез *jsonPath()*.

### Проверка на controller тестове, генерирани с ИИ

Генерираният controller тест трябва да бъде оценен спрямо задачата, действителния API договор и избраното ниво на тестване.

Трябва да се провери дали:

•	HTTP методът и URL съответстват на действителния API;

•	request данните, validation сценариите, HTTP status и response body съответстват на API договора;

•	поведението на mock-натия service е подходящо за проверявания сценарий;

•	тестът проверява web слоя, без да дублира бизнес логиката от unit тестовете;

•	не се използва ненужно @SpringBootTest или друга инфраструктура;

•	ИИ не е добавил endpoints, полета, status кодове или друго API поведение, което не съществува в приложението.

Успешното изпълнение на controller тест не доказва коректността на бизнес логиката зад mock-натия service и не замества тестовете на останалите нива.
