### Подготовка на frontend проекта

Frontend приложението да бъде създадено в директория frontend/ в основната директория на съществуващия Maven проект:

```
project-root/
├── frontend/
├── src/
│   ├── main/
│   └── test/
└── pom.xml
```

Backend и frontend приложенията ще се стартират независимо:

Spring Boot    → localhost:8080

React / Vite   → localhost:5173


За разработването на клиента да се използват:

•	React;

•	TypeScript;

•	Vite;

•	стандартният fetch API.

Да не се добавят допълнителни библиотеки за управление на състояние, маршрутизиране, HTTP комуникация или изграждане на потребителския интерфейс.

Да се възложи на ИИ агента създаването на минимален React проект с TypeScript и Vite в директория frontend/. На този етап да не се реализира комуникация с backend приложението или функционалността на клиента.

Преди прилагане на предложените действия да се провери дали те съответстват на поставената задача и технологичните ограничения. След изпълнението да се провери действителното състояние на проекта и дали frontend приложението се стартира успешно.

### Подбор на backend артефакти за разработване на клиента

Клиентът трябва да поддържа две операции от съществуващото REST API:

•	извличане на съществуващите заявки за услуги;

•	създаване на нова заявка за услуга.

Преди генериране на клиента да се идентифицират backend артефактите, съдържащи информацията, необходима за тези операции.

Да се установят:

•	използваните REST endpoints и HTTP методи;

•	request и response данните;

•	типовете и допустимите стойности;

•	приложимите validation правила;

•	начинът, по който API представя възникналите грешки;

•	необходимата конфигурация за комуникация между frontend и backend приложенията.

Самостоятелно да се подбере релевантният project context. Да не се предоставя автоматично целият backend проект.
С помощта на ИИ агента да се анализира задачата и да се предложи минимална структура на React клиента. На този етап да не се генерира код.

Предложението да се провери спрямо backend артефактите и ограниченията на задачата. Да се установи дали използва действителния API договор, дали не въвежда несъществуващи endpoints, полета или поведение и дали не предлага промяна на backend API единствено за удобство на клиента.

При липсваща информация да се определи какъв допълнителен контекст е необходим и да се добавят само релевантните артефакти.

### Генериране на React клиента

На базата на извършения анализ да се разработи минимален React клиент, който:

•	извлича съществуващите заявки за услуги чрез наличната GET операция;

•	позволява създаване на нова заявка чрез наличната POST операция;

•	визуализира получените заявки;

•	предоставя форма за въвеждане на необходимите данни;

•	обработва и визуализира грешките, върнати от backend приложението.

Преди генериране на кода самостоятелно да се определи необходимият контекст от съществуващите *backend и frontend артефакти*. Backend артефактите определят API договора, а frontend артефактите – текущата структура и реализация на клиента.

Да се възложи на ИИ агента реализацията на клиента в рамките на определения scope и технологичните ограничения.

Преди прилагане на предложените промени да се провери:

•	кои файлове ще бъдат създадени или променени;

•	дали промените са необходими за поставената задача;

•	дали се използват само съществуващите REST операции;

•	дали се предлагат ненужни библиотеки, компоненти или архитектурни елементи;

•	дали се предлагат несвързани промени или промени в backend API.

След одобрение да се приложат необходимите промени и да се провери действителното състояние на проекта.
Наличието на backend и frontend артефакти в контекста не трябва да се приема като гаранция, че ИИ ги е използвал правилно. Генерираната реализация трябва да бъде проверена спрямо самите артефакти.

### Проверка на съответствието с API договора

След генериране на React клиента да се провери дали той използва коректно съществуващия REST API.

Да се сравни генерираният frontend код с backend артефактите и да се провери:

•	дали HTTP методите и URL адресите съответстват на реалните REST операции;

•	дали TypeScript типовете и изпращаните данни съответстват на request и response DTO обектите;

•	дали се използват действително допустимите стойности;

•	дали HTTP response и грешките се обработват според API договора;

•	дали не са добавени несъществуващи полета, endpoints или поведение;

•	дали във frontend клиента не е дублирана backend бизнес логика;

•	дали направените промени остават в определения scope.

При установено несъответствие да се приложи root-cause analysis и да се установи причината преди извършване на промяна. Причината може да бъде в предоставения контекст, интерпретацията му от ИИ, генерираната реализация или конфигурацията на комуникацията между приложенията.

При недостатъчен контекст да се добави само необходимата информация и да се извърши минималната корекция за установения проблем.

Съществуващият backend API да не се променя единствено с цел генерираният frontend код да заработи.

### Проверка чрез изпълнение

След извършване на необходимите корекции да се стартират Spring Boot приложението и React клиентът.

Чрез реално изпълнение да се проверят:

- зареждането на съществуващите заявки;

- създаването на валидна нова заявка;

- поведението при невалидни входни данни;

- визуализирането на response или грешката, върнати от backend приложението.

Успешното стартиране на двете приложения не е достатъчно доказателство за коректна интеграция. Наблюдаваното поведение трябва да бъде сравнено със съществуващия API договор.

При установено несъответствие да се приложи root-cause analysis преди промяна на frontend или backend реализацията.

### Финална проверка

След приключване на работата да се провери дали:

•	React клиентът използва действителния API договор и данните съответстват на backend артефактите;

•	frontend приложението не дублира backend бизнес логика и не въвежда неподдържано поведение;

•	използваният project context е релевантен за конкретната задача, а решенията на ИИ са проверени спрямо предоставените артефакти;

•	приложените промени остават в определения scope и не въвеждат ненужни зависимости или архитектурни усложнения;

•	при установени проблеми е анализирана причината преди извършване на корекция;

•	комуникацията между frontend и backend приложенията е проверена чрез реално изпълнение.
