# Лабораторно упражнение 9

## Разработка на клиент спрямо съществуващ API с помощта на ИИ

### Цел

Целта на упражнението е да се изследва използването на съществуващи софтуерни артефакти като контекст при разработване на нов компонент с помощта на ИИ асистент.

Чрез разработване на клиент към съществуващо REST API ще бъде разгледано как реални артефакти от проекта могат да осигурят grounding на генерираното решение спрямо действителното състояние на системата. Ще бъде проверено дали при разработването на новия компонент се запазва съществуващият API договор, без да се въвеждат неподдържани endpoints, структури от данни или поведение.

Практическата задача е разработване на минимален React клиент към съществуващото Spring Boot приложение, който използва наличното REST API за извличане и създаване на заявки за услуги.

### React клиент към REST API

React позволява изграждане на потребителски интерфейс чрез компоненти. При функционалните компоненти *useState* може да се използва за управление на състоянието, а *useEffect* – за изпълнение на действия като първоначално извличане на данни.

React клиентът може да комуникира с REST API чрез стандартния fetch API. При изпращане на заявка трябва да бъдат съобразени HTTP методът, URL, request body и необходимите headers, а полученият response трябва да бъде обработен според неговия status и съдържание.

При използване на TypeScript могат да бъдат дефинирани типове за данните, изпращани към и получавани от REST API. Тези типове трябва да съответстват на действителния договор на backend приложението.

Frontend и backend приложенията могат да се разработват и стартират независимо. Когато работят на различни портове, комуникацията между тях трябва да бъде конфигурирана чрез подходящ механизъм, например proxy на development server или CORS конфигурация.

### Софтуерни артефакти като контекст и grounding

При работа по съществуваща система контекстът за ИИ асистента може да бъде предоставен чрез реални софтуерни артефакти, а не чрез повторно текстово описание на вече съществуващата реализация.

Такива артефакти могат да бъдат:

•	controller класове;

•	request и response DTO класове;

•	enum типове;

•	validation правила;

•	модели за представяне на грешки;

•	конфигурационни файлове;

•	тестове или други артефакти, които описват използвания договор.

*Grounding* означава генерираното решение да бъде основано на предоставена проверима информация за конкретната система, а не само на общите знания и предположения на модела.

При разработване на клиент към съществуващо REST API backend артефактите могат да предоставят информация за действителните endpoints, HTTP методи, структури на request и response данните, допустими стойности и формата на грешките.

Не всички налични артефакти са необходими за всяка задача. Подбира се само контекстът, необходим за конкретната промяна. Наличието на даден артефакт в контекста също не гарантира, че ИИ ще го интерпретира правилно, поради което генерираното решение трябва да бъде проверено спрямо източника, на който се предполага, че е основано.

### Запазване на съществуващия API договор

Когато нов компонент използва съществуващ интерфейс, генерираното решение трябва да спазва неговия договор.

При REST API договорът включва например:

•	HTTP методите и URL адресите;

•	структурата на request и response данните;

•	имената и типовете на полетата;

•	допустимите стойности;

•	HTTP status кодовете;

•	структурата на отговорите при грешка.

Когато задачата е разработване на клиент към съществуващ API, несъответствие между генерирания клиент и backend договора не трябва автоматично да води до промяна на backend приложението. Първо трябва да бъде установена причината за несъответствието.

Frontend приложението може да съдържа логика, свързана с потребителския интерфейс и управлението на неговото състояние, но бизнес правилата остават отговорност на backend приложението.

### Проверка на генерираното решение

Генерираният frontend код трябва да бъде проверен както спрямо backend артефактите, така и чрез реална комуникация със съществуващото приложение.

Трябва да се установи дали клиентът:

•	използва съществуващите REST операции и съответстващите им структури от данни;

•	използва допустимите стойности от backend модела;

•	обработва response и грешките според действителния API договор;

•	не дублира ненужно backend бизнес логика;

•	не въвежда неподдържани функции, зависимости или архитектурни усложнения.

Успешното стартиране на React приложението не доказва, че интеграцията е коректна. Необходимо е да бъдат изпълнени реални операции към backend приложението.
