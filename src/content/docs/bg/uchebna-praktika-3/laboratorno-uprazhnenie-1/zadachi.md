### Задача

Да се разработи REST приложение за управление на заявки за услуги. Клиентите трябва да могат да подават заявки за услуги, а служителите на офиса да могат да преглеждат постъпилите заявки. Приложението ще бъде разширявано с допълнителна функционалност в следващите упражнения.

Началната версия на приложението ще бъде създадена чрез поредица от експерименти с ИИ асистент, при които ще се променят конкретността на поставената задача и предоставеният контекст. Получените решения ще бъдат сравнявани, анализирани и проверявани.

### Експерименти

При провеждане на първите три експеримента всеки експеримент се започва с нова Agent сесия. По този начин резултатът от текущия експеримент няма да използва разговорен контекст, натрупан при предходния.

При първите два експеримента се използва нов Java проект без разработена приложна функционалност. При третия се използва предварително създаден минимален Maven проект.

Промптовете се подават във вида, в който са дадени в условието.

Поради недетерминистичния характер на генеративните модели не се очаква различните изпълнения да произведат идентични решения. Сравняват се направените избори и предположения, а не точното съдържание на генерирания код.

*Експеримент 1: минимален контекст*

Да се създаде нов Java проект без разработена приложна функционалност и да се започне нова Agent сесия.

Да се подаде следният промпт:

```text
Create REST app that handles client requests.
```

Да се наблюдават предложените от Agent действия и генерираното решение, без предварително да се коригират.

Да се анализира:

•	какви технологии е избрал ИИ асистентът; 

•	каква структура на приложението е предложил; 

•	какви класове, файлове или други артефакти е създал или предложил; 

•	какъв модел на заявката е предположил; 

•	какви операции е реализирал; 

•	кои решения произтичат пряко от поставената задача; 

•	кои решения представляват предположения; 

•	има ли непоискани решения или функционалност. 

Да се определи коя липсваща информация би ограничила направените предположения.

*Експеримент 2: добавяне на технологичен контекст*

Да се започне от нов Java проект без разработена приложна функционалност и нова Agent сесия.

Да се подаде:

```text
Create a Spring Boot REST application for managing service requests.
Use Java 26, Maven, Spring Web, Spring Data JPA, Lombok, H2 and validation.
The application should be called ServiceRequestManagementSystem.
```

Да се анализират заявката и полученият резултат по въведените критерии. Допълнително да се провери:

•	създаден или предложен ли е Maven проект с необходимите зависимости; 

•	как са организирани пакетите; 

•	има ли разделение между controller, service и repository; 

•	използвани ли са DTOs; 

•	какъв модел на заявката е предложен; 

•	какви REST endpoints са реализирани; 

•	кои технологични решения вече са определени от предоставения контекст;

•	какви функционални и архитектурни решения ИИ продължава да взема самостоятелно. 

Да се сравни резултатът с първия експеримент и да се определи кои предположения са ограничени чрез добавения технологичен контекст и за кои части от решението все още липсва информация.

Полученият проект на този етап се използва за анализ и сравнение и не е необходимо предложените промени да бъдат приети и приложението да бъде довършено.

*Експеримент 3: функционален, технологичен и архитектурен контекст*

Да се създаде нов минимален Maven проект със:

•	GroupId: com.example 

•	ArtifactId: ServiceRequestManagementSystem 

•	Java: 26 

В началния pom.xml не се добавят Spring Boot или други зависимости.

Да се започне нова Agent сесия. Файлът pom.xml да бъде добавен изрично към контекста на задачата.

Да се подаде следният структуриран промпт:


```text
### Task
Convert the existing Maven project into a Spring Boot REST application for managing service requests.

### Context
Use Java 26, Spring Web, Spring Data JPA, Lombok, H2 and validation.
Use the following packages: controller, dto, entity, repository, service.
ServiceRequest is the main entity. Properties: id, customerEmail, description, serviceType, executionMode, priority, status, submittedAt.
ServiceType: INSTALLATION, REPAIR, CONSULTATION.
ExecutionMode: REMOTE, ON_SITE.
Priority: STANDARD, URGENT.
RequestStatus: SUBMITTED.
A new request is created with status SUBMITTED. submittedAt is set by the system. The customer does not provide id, status or submittedAt.
Required endpoints:
POST /api/requests
GET /api/requests
GET /api/requests/{id}

### Constraints
Do not add functionality that is not required above.

### Expected output
Create or modify only the files needed for this initial version of the application.
```

Преди предложените от Agent промени да бъдат приети, заявката и резултатът да се оценят по въведените критерии.

Допълнително да се провери:

•	съответства ли структурата на зададения архитектурен контекст; 

•	реализирани ли са зададените REST endpoints; 

•	съответства ли ServiceRequest на зададения модел; 

•	спазени ли са началният статус и системно задаваните стойности; 

•	предложени ли са необходимите зависимости и конфигурация; 

•	добавени ли са непоискани компоненти или функционалност; 

•	има ли изискване, което Agent не е спазил. 

Да се сравни предложеното решение с резултатите от първите два експеримента. Да се определи кои предположения са ограничени чрез добавения функционален и архитектурен контекст и кои решения моделът продължава да взема самостоятелно.

След анализа да се прегледат предложените действия и промени. Да се приемат само тези, които съответстват на поставената задача.

Ако решението е непълно или некоректно, да се установи конкретният проблем и да се формулира 
уточняваща заявка само за необходимата промяна, вместо да се генерира отново цялото приложение.

### Проверка и отстраняване на проблеми

След създаване на проекта да се извърши verification на полученото решение:

•	да се прегледат действително създадените и променените файлове; 

•	да се провери съответствието им със зададените изисквания; 

•	да се компилира и стартира приложението; 

•	да се проверят основните REST endpoints; 

•	при възникване на грешка да се анализират действителното съобщение, кодът и конфигурацията; 

•	при необходимост да се използва ИИ асистентът за формулиране на възможни причини; 

•	предложената от ИИ причина да се разглежда като хипотеза, която трябва да бъде проверена; 

•	да се установи действителната причина (root cause) преди приемане на корекция; 

•	да се извърши само необходимата корекция и тя да бъде проверена повторно. 

Тази последователност представлява процес на debugging, при който ИИ асистентът може да подпомага анализа, но установяването на действителната причина и проверката на корекцията остават част от инженерната работа на разработчика.

Твърдението на ИИ асистента, че приложението се компилира или работи успешно, не се приема като доказателство за това.
