# Упражнение 7 — Version Control, CI/CD и автоматизация

## Теория

### 1. Версии и съвместна работа

1. **Commit и клон.** Commit е проверим набор промени; клонът изолира работа. Commit съобщението обяснява поведението и причината, а не само списък файлове.
2. **Pull request и review.** Прегледът проверява изискванията, рисковете, тестовете и документацията. Зелен pipeline не заменя преглед на бизнес правилата.
   - **Пример:** тестовете минават, но предложението за категория вече се записва автоматично — това противоречи на SRS.
3. **Конфликт.** Две текстови промени може да се слеят успешно и да остане логически конфликт. След merge се проверяват код, API договор и UML модел.

### 2. CI/CD и quality gates

**Continuous Integration** проверява интеграцията при промяна. **Continuous Delivery** подготвя проверен артефакт за внедряване; **Continuous Deployment** го внедрява автоматично. За учебния проект външно публикуване не е необходимо; достатъчна е възпроизводима локална среда.

Pipeline има зависимости: Java тестове и Python проверки → integration сценарий → пакетиране. Провалът на която и да е задължителна проверка блокира следващия етап. Gate върху macro-F1 използва реалния отчет от тема 6, а не подставена стойност.

### 3. Среда, кеш и артефакти

1. **Възпроизводимост.** Записваме Java/Python версии, зависимости, конфигурация и идентичност на данните. Maven Wrapper фиксира Maven, а Python lock файлът — пакетите.
2. **Кеш и артефакт.** Кешът ускорява зависимостите; артефактът е резултат от конкретното изпълнение. Стар отчет от кеша не доказва текущ успех.
3. **Secrets.** Пароли и signing ключове се подават чрез локална среда или CI secrets. Не се записват в YAML, диаграми или логове.

## Примерен проблем

На единия компютър Task Manager работи, а на другия Python услугата използва различна версия на библиотеките. Тестовете минават само ако остане база от предишно стартиране.

### Стъпка 1. Фиксиране на входовете

Продължете [тема 6](/courses/bg/software-engineering-ai/laboratorno-uprazhnenie-6/). Запишете команди за чисто изпълнение на Java и Python тестовете, инсталиране от lock файла и обучение с фиксираните данни. Всеки тест създава и почиства собствените си данни. Добавете командите в README на студентското решение.

### Стъпка 2. Контейнеризация на AI услугата

Добавете Dockerfile в `ai-service`, който инсталира фиксираните зависимости и стартира избрания WSGI сървър, слушащ на порт 8000. Добавете и него в lock файла. Не използвайте development/debug режим. Добавете Compose услуга `category` на backend мрежата и read-only mount за обучен артефакт. Spring използва конфигурируем URL `http://category:8000`; този вътрешен порт няма нужда от публикация към хоста.

### Стъпка 3. Подреждане на проверките

Опишете pipeline в `.github/workflows/ci.yml` или друга избрана CI система. Java и Python проверките могат да са независими, но пакетиране има зависимост от двете. Използвайте `./mvnw verify` за Java, а за Python — собствените команди за валидация на данни, обучение и тестове. Докажете, че всяка команда връща ненулев exit code при провал.

Примерна логическа последователност, която трябва да реализирате с действителните имена на файловете:

```text
checkout → Java tests ───────────┐
         → Python/data/ML tests ├→ isolated E2E → image build → reports
                               ┘
```

### Стъпка 4. Проверка на чиста среда

Използвайте отделен Compose проект `se-task-manager-ci`, отделна тестова конфигурация и свободен порт, например 19001. Всички start/log/stop команди за този прогон използват това име. След readiness проверките изпълнете E2E сценария. Почистването се изпълнява и при провал; унищожават се само тестови данни, не работният volume `se-task-manager`.

### Стъпка 5. Доказване на блокиране

Направете временна промяна, която нарушава теста за предложение без запис. Запазете неуспешния CI резултат и покажете, че няма нов успешно публикуван артефакт за този commit. Възстановете кода и запазете успешния прогон. Deployment диаграмата се актуализира според действителните услуги и мрежи.
