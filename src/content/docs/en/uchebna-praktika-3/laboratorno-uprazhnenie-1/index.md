# Laboratory Exercise 1

## The Influence of Context on AI-Assisted Software Generation

### Objective

The objective of this exercise is to examine how prompt formulation and the provided context influence the software solution generated by AI. By progressively adding technological, functional, and architectural context, the solutions and assumptions made by the AI assistant at different levels of task specificity will be compared.

During the exercise, the initial version of a Spring Boot REST application for managing service requests will be created. The generated solutions will be analyzed and verified by reviewing the proposed changes and the code, compiling and running the application, before they are accepted as the basis for the subsequent exercises.

### Brief Introduction to Working with Generative AI

Generative models can create text, source code, and other outputs based on the information provided to them and the assigned task. In software development, they can be used through AI assistants integrated into the development environment or available as standalone applications.

The instruction or request submitted to the model is commonly referred to as a prompt. In addition to the task itself, the model may also have access to additional information – context – required to perform the task. Context may include, for example, functional requirements, technologies being used, architectural decisions, source code, or information from previous interactions with the AI assistant.

A prompt and context are not the same thing. The prompt specifies what the model is expected to do, while the context provides the information required to perform the task.

Language models process the provided information as a sequence of tokens. The amount of information a model can use in a single interaction is limited by its context window. Therefore, when working on a software project, it is important to provide context that is relevant to the specific task instead of automatically including all available information.

The context window limitation is not the only reason why a particular instruction may not be followed. When the context is large or overloaded with irrelevant information, individual pieces of information may not sufficiently influence the generated result, while instructions from earlier parts of the interaction may be omitted or applied incorrectly. Therefore, the presence of information in the context does not guarantee that the model will use it correctly.

### Basic Prompting Techniques

When working with generative AI, different prompting techniques can be used depending on the nature of the task and the available information.

Zero-shot prompting means assigning a task without providing an example of the expected result. With one-shot or few-shot prompting, one or more examples are added to the task to demonstrate the desired execution approach, structure, or output format.

With role prompting, the model can be assigned a particular role or perspective when this provides useful guidance for performing the task. Assigning a role by itself does not guarantee higher quality or correctness of the generated result.

With structured prompting, the individual parts of the prompt are clearly separated according to their purpose. The following basic structure will be used in the exercises:

•	Task – defines the task that the AI should perform; 

•	Context – provides the relevant information required to perform the task; 

•	Constraints – defines the conditions and boundaries that must be observed; 

•	Expected output – defines the expected result and, when necessary, the way in which it should be presented. 

The structure serves as a basic framework and is adapted to the specific task. It is not necessary for every part to appear as a separate heading in every short prompt. For more complex tasks, the individual parts can be clearly separated using headings or other delimiters.

The choice of technique and the necessary prompt elements depend on the specific task. Using a particular structure does not eliminate the need to verify the generated result.

### Context and Model Assumptions

When a task does not define a particular aspect of the solution with sufficient specificity, the model may fill in the missing information using its own assumptions. For example, when asked to create a REST application without specifying a language, framework, data model, or architecture, the AI assistant may choose these independently.

Missing context is information required to perform the task but which has not been provided or is not accessible. An assumption is a choice or supposition made by the model when information has not been defined unambiguously. Such an assumption may turn out to be appropriate, but it must be identified and verified.

An AI statement that is not sufficiently supported by the provided context or by verifiable results is an unsupported claim. When the model generates false or nonexistent information and presents it as fact, the result may be described as a hallucination.

An assumption, an error, and an unsolicited solution are also not equivalent. An assumption fills in information that has not been defined unambiguously. An error contradicts a requirement or leads to a technically incorrect result. An unsolicited solution is functionality, a component, or another choice that was not requested, regardless of whether it is technically correct in itself.

Increasing the specificity of the task and providing relevant context can limit some of the assumptions. However, this does not mean that a longer or more detailed prompt automatically leads to a better solution.

Generative models are nondeterministic. With identical or very similar input information, different runs may produce different results. Variability may also depend on model parameters and its configuration, such as temperature. These parameters will not be adjusted during the exercises. When comparing results, identical classes, structures, or code are not expected – the solutions and assumptions made are compared instead.

AI-generated output should not be accepted as correct merely because it appears plausible or because the AI assistant claims that the solution works. The result must be checked using means appropriate to the task (verification) – for example, code review, comparison with the requirements, compilation, execution, and automated tests.

### Evaluating the Request and the Generated Result

The quality of the prompt and the quality of the generated result are evaluated separately. A well-formulated request does not guarantee a correct result, while an acceptable result does not necessarily mean that the request was sufficiently clear and complete.

When evaluating the request, check whether:

•	the task is defined clearly and specifically; 

•	the necessary and relevant context has been provided; 

•	the important constraints and the scope of the task have been defined; 

•	it is clear whether a new component should be created or an existing one should be modified; 

•	the expected result has been defined clearly enough; 

•	there are any contradictory or ambiguous requirements. 

When evaluating the result, check whether:

•	the specified requirements have been fulfilled; 

•	any functionality is missing or implemented incorrectly; 

•	the AI has made any assumptions; 

•	unsolicited components or functionality have been added; 

•	technological, architectural, and other constraints have been observed; 

•	the solution contains technical errors or inconsistencies; 

•	anything must be verified before the result can be accepted. 

The AI assistant's explanation of the actions performed must also be checked against the actual state of the project. A claim that only a particular file was modified, that all requirements were fulfilled, or that the application runs successfully is not accepted as evidence by itself.

These criteria will also be used in the subsequent exercises and, when necessary, will be supplemented with criteria specific to the particular task.

### Engineering Process for Working with AI

When using an AI assistant in software development, the exercises will follow a general engineering process:

*task → context → analysis → decision → implementation → verification → refinement*

First, the task and its scope are defined, and the necessary context is selected. The AI's proposals and actions are analyzed before deciding which of them should be accepted. The implementation is verified using means appropriate to the task. When a problem or inconsistency is identified, its cause is analyzed, the necessary additional context is provided, and the required refinement or correction is performed.

The process is iterative, and the individual steps are applied according to the nature and complexity of the specific task.

### Working with the AI Assistant

The exercises will use a local AI assistant in the IntelliJ IDEA development environment. The DevoxxGenie extension is used to interact with the model, while Ollama provides local execution of Ministral 3 3B.

At the beginning of the exercise, the AI assistant is configured to work with the local model. The tools available to the Agent and the settings for approving actions are examined. Actions proposed by the Agent are reviewed before they are executed.

The primary mode of operation in the exercises is Agent mode. In this mode, the AI assistant can use the provided context, inspect parts of the project, and propose actions such as creating or modifying files.
Different AI assistants and agents may use different mechanisms for automatically retrieving context from the project. Access to the entire project does not necessarily mean that all of its elements are used as context when performing a particular task. The context used depends on the specific tool, mode of operation, model, and its configuration.

In the exercises, the student defines the task and manages the relevant context. The Agent proposes actions and changes that must be reviewed before being accepted. After they are applied, the actual state of the project is verified.

When performing a specific task, existing project files relevant to its execution can be added to the context. Selecting the context is part of formulating the task, and it is not necessary to automatically provide all project files.

Reviewing and accepting the changes proposed by the Agent does not replace the use of version control. Version control systems provide an independent history of changes and the ability to return to a previous state of the project. In the exercises, version control management is not a separate learning task.

The principles covered in the exercises – task formulation, context management, analysis of assumptions, critical evaluation, and result verification – do not depend on a particular AI assistant or language model.
